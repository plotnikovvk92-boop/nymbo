## Исправления

Оплата остаётся redirect ЮKassa, 89.00 RUB, capture=true. Telegram Payments больше не выдаёт доступ; старый successful_payment направляет в поддержку для проверки.

Существующий payment_id проверяется GET. Для первого POST атомарно сохраняются ключ и точные параметры запроса; повтор после таймаута использует тот же ключ/параметры, даже после изменения версии оферты или return URL. Отменённый checkout закрывается; следующий клик создаёт новый заказ. Pending/waiting_for_capture не выдают доступ. Потерянный ответ старше безопасного окна 23 часа и старые незавершённые запросы без сохранённого payload блокируются до проверки поддержки, чтобы не создать новую покупку после истечения идемпотентности.

Webhook не доверяется объекту уведомления: платёж получает сервер из API. Проверяются id, succeeded, paid=true, 89 ₽, RUB, metadata.user_id, recipient.account_id и строгое соответствие boolean test режиму бота. Новый платёж должен соответствовать текущему локальному intent/payment_id или сохранённому order_key при потерянном ответе. Владелец из webhook сам по себе недостаточен.

Запись платежа и выдача доступа — одна SQLite-транзакция с BEGIN IMMEDIATE. Уже записанный payment_id больше не меняет paid, дату периода, оферту или меню. Это действует после истечения, ручного отзыва, удаления профиля и повторной регистрации. Отзыв/ручная выдача также выводят старый pending-intent из обработки, а транзакция выдачи перепроверяет его статус: поздний необработанный платёж не отменяет админ-решение. Если клиент всё же оплатит внешнюю старую ссылку после отзыва/ручной выдачи, потребуются проверка поддержки и решение по возврату; автоматического возврата комплект не делает.

Новая покупка удаляет прошлые plan/shopping, формирует новый актуальный период. Сохранение плана проверяет revision и paid: запоздавшая генерация не возвращает удалённый/отозванный план. Изменение калорийности или исключений инвалидирует оба старых JSON. БЖУ/калорийные формулы и каталог MEALS не изменены — проверено по AST функций и побайтовому сравнению каталога (formula_verification.json).

Сбой генерации не теряет оплату; повтор webhook, фоновая сверка и /start восстанавливают план без нового срока. Сбой отправки с определённым результатом разрешает повтор сообщения; параллельные/повторные webhook после успешной отправки не отправляют повтор. При неоднозначном сетевом таймауте Telegram сообщение автоматически не повторяется: отправку нельзя гарантировать exactly-once через API Telegram. Доступ/план сохранены и доступны через /start.

Восстановление пропущенного webhook: фоновый GET известных платежей, /start и отдельная кнопка «Проверить оплату». Return URL исключительно информирует, не обращается в API и не пишет доступ. Платёжные задачи выбираются с учётом последней проверки, чтобы одна старая запись не занимала очередь постоянно.

## Запуск и данные

С согласия пользователя подготовлен Passenger с постоянно работающим event loop в отдельном потоке. Параллельные WSGI-запросы отправляют coroutine в один loop; проверен запуск ровно один раз при восьми конкурентных запросах и выполнение фоновой задачи в простое. Поток создаётся лениво после появления worker PID, не при импорте до fork.

FSM перенесён в существующую SQLite. Ключ включает bot/chat/user/thread/business_connection/destiny; событие пользователя защищается общей SQLite lease с продлением, включая несколько worker. Перезапуск сохраняет анкету; завершение, сброс и /delete_data очищают её. Фактическое временное хранение анкеты в SQLite отражено в черновиках документов. На Beget ещё нужно подтвердить живучесть процесса: Passenger может выгружать idle worker, и тогда поток тоже прекращается. Нужна поддерживаемая настройка постоянного процесса или отдельно согласованный cron; в этом комплекте cron не установлен.

Startup больше не очищает старые поля клиентской БД/PDF и не вызывает DeleteWebhook/SetWebhook. Существующий URL проверяется и при несовпадении запуск отклоняется. Webhook нельзя переключить случайным перезапуском второй среды. Polling отказывается запускаться при существующем webhook. Исправлен вызов aiohttp startup/shutdown через dispatcher hooks.

Миграции аддитивные. created_at не изменяется ручной выдачей/отзывом. Старые анкеты из legacy колонок автоматически не стираются. Удаление данных старше двух месяцев не добавлено.

Срок сохранён как **30 календарных дней**, в соответствии с исходным кодом и архивной офертой. Таймзона по умолчанию Europe/Samara, независимо от timezone сервера. Покупка 10 октября активна по 8 ноября включительно, 9 ноября уже неактивна. Это не ровно 720 часов от момента оплаты. Исходное правило пересчёта «с завтрашнего дня» также сохранено; на последнем календарном дне для пересчёта уже нет последующих дней. Если нужен другой смысл срока/пересчёта, требуется отдельное согласование.

Все ветки просмотра меню проверяют доступ, включая неделю/день/сегодня. Демо разрешено только для однодневного плана. Старые индексные кнопки читают текущий план; удалённый профиль ничего не раскрывает. PDF формируется в уникальном временном файле, поддерживает кириллицу и актуальные даты/меню, после отправки файл удаляется. Регистрация шрифтов защищена от параллельных потоков.

Название по умолчанию «Нямбо», поддержка @gymochka_admin. TEST_MODE/skip_pay сохранён и кнопка показана только в тестовом режиме. Production админ — только числовые IDs. Админ-выдача/отзыв сохраняются; выдача при невозможном плане не отзывает старый действующий доступ. Перед отправкой напоминания повторно проверяются оплаченный статус, согласие и свежая активность; резервирование одноразовое.
